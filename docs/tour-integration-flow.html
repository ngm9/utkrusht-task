Utkrusht · Task Generation Pipeline

Generating the candidate tour inside the pipeline

Every task the pipeline creates lands with its candidate walkthrough (tasks.tour) already attached — generated inline in creator.py. This covers sandbox tasks and frontend / non-infra tasks alike.

Important: backfill_task_tours.py is reference only — it is a one-off script and will be removed. Nothing may import from it. All tour logic is written fresh into a new, self-contained module: generators/task/tour.py. The backfill script serves only as the spec — prompt shape, boilerplate, decision logic, validation rules.
Every task gets a tour — not just infra. Infra tasks (Docker / shared infra + template) get a sandbox tour; non-infra tasks — frontend (React, Next.js), library-only backend (LangChain, pure Python) — get a local (clone-and-run) tour. Both are first-class outputs of the same step. Tours are skipped in exactly two cases: an infra task with no built template (its sandbox can never boot), and PR_REVIEW tasks — deferred for now until we finalise how PR-review tours should work.
01

The whole thing in simple words — step by step

First, what is a "tour"?

Imagine a candidate (a person taking a coding test) opens a task for the first time. They see a bunch of code files and have no idea what to do. A tour is like a little instruction card that tells them: (1) "Here's your code, open it here" → (2) "Run this command to start the app" → (3) "Run this command to see the tests (they fail right now — your job is to fix that)" → (4) "When you're done, push your code to submit". That's it. The tour is just a small step-by-step guide saved in the database next to each task (tasks.tour).

The problem we're solving

Every task is different — one uses Python, one uses React, one has a database, one doesn't. So we can't write one guide for all tasks; we need a custom guide for each task. Writing them by hand for hundreds of tasks is too slow, so we make an AI write them. But AI sometimes lies (it might say "run npm test" when the project has no tests). So we can't just trust it — we have to check its work before saving.

Step by step, what happens

  1. A new task gets created. The pipeline generates a coding task — this already existed before this feature. The tour step rides along with it.
  2. Decide what kind of guide this task needs. Three possibilities: the task runs in a cloud sandbox (a computer in the browser) → write a "sandbox" guide. The task is done on the candidate's own laptop → write a "local" guide (clone the repo, install, run). Some tasks get no guide for now (PR-review tasks, or an infra task whose sandbox can never boot) → skip.
  3. Split the guide into fixed parts and custom parts. The beginning ("open your editor", "here's your repo") and the end ("commit and push to submit") are the same for every task, so they're written by us, in code, once. The AI never touches them — this way they can never be wrong. Only the middle ("how to run this specific project") is written by the AI.
  4. Show the AI the task's files. We give the AI the actual code files of the task (README first, then config files, then source code) and say: "Write ONLY the middle steps, based on these real files. Don't make anything up. And don't reveal the answer to the task!"
  5. Check the AI's answer with simple rules (no AI needed). Code checks things like: Is it valid JSON in the right shape? Is it short enough? (max 7 sections total — it's a guide, not a book.) Did it use only allowed placeholder links? Did it add useless fluff like "explore the codebase"? → rejected.
  6. A second AI acts as a judge. We show the tour + the code files to another AI and ask: "Is everything in this guide TRUE? Does every command, file, and port actually exist in this project? Does it accidentally reveal the solution?" If the judge says no → fail.
  7. Actually test it for real. The coolest part. For sandbox tasks: the task was just booted in a real cloud sandbox (to test that it builds). While that sandbox is still alive, we literally run the tour's commands inside it. If the guide says "run docker-compose up", we run it. If it breaks → the guide is wrong → fail. (One exception: the test command is allowed to fail, because tests are supposed to be red at the start.) For local tasks: we can't run it on the candidate's laptop, so instead we cross-check: if the guide says npm run dev, we open package.json and verify a dev script really exists. If not → fail.
  8. If any check fails, try again. We tell the AI exactly what was wrong ("you said npm test but there's no test script") and let it try again. Up to 3 tries (MAX_TOUR_EVAL_RETRIES).
  9. Save — or give up gracefully. If a tour passes all checks → save it to the database with the task. If all 3 tries fail → save the task without a tour (the tour field stays empty). Important rule: a broken tour must never block a good task. The task still ships; it just has no guide.
The one-line summary: when a task is created, an AI writes a short "how to get started" guide from the task's real files, then code rules + an AI judge + actually running the commands verify it's true, and only a verified guide gets saved — if it can't be verified, the task ships without one.

The same logic as pseudocode

# generators/task/tour.py — self-contained, no backfill import
def generate_tour(code_files, meta):
    kind = decide_kind(meta)                      # §05 — sandbox / local / skip (PR_REVIEW → skip for now)
    if kind == "skip": return None

    repo_text = render_code_files(code_files)     # §01 step 2 — in-memory, no GitHub
    surfaces  = surfaces_block(meta["expected_ports"]) if kind == "sandbox" else ""

    critique = None
    for attempt in range(MAX_TOUR_EVAL_RETRIES):  # eval-gated retry loop, like evals.py
        raw    = llm_via_portkey(build_middle_prompt(kind, meta, surfaces, repo_text, critique))
        middle = parse_and_validate(raw, kind)    # §07 layer 1 — deterministic, abort on violation
        tour   = assemble(HEAD[kind], middle, TAIL[kind])

        verdict = eval_tour(tour, repo_text, kind)  # §07 layer 2 — LLM judge, grounded in the repo
        if verdict.passed and kind == "sandbox" and sandbox is not None:
            verdict = run_tour_in_sandbox(tour, sandbox)  # §07 layer 3 — execute steps in the gate's live sandbox
        elif verdict.passed and kind == "local":
            verdict = check_against_manifests(tour, code_files)  # §07 layer 3 — npm/pip/mvn vs real manifests

        if verdict.passed: return tour
        critique = verdict.critique               # judge critique OR the failing command's output

    return None                                   # retries exhausted → no tour (non-fatal)

02

Where every input comes from — and where the tour goes

Every value the tour logic needs is already produced by the pipeline before the tour step runs — nothing new is computed, nothing is fetched from outside. This is the exact data flow:

ValueProduced where in the pipelineUsed for
code_files Task-generation LLM output — task_data["code_files"], after the README scrub. The exact files pushed to GitHub. The file blob that grounds the prompt (real services, ports, commands, seed scripts).
is_shared_infra_required has_shared_infra_files(code_data) in creator.py — true iff the generated repo carries Docker / docker-compose files. Consistent with task_shape, which the pipeline fixes when generation starts. Kind decision: infra task (sandbox) vs non-infra / frontend task (local) — same source of truth the E2B gate uses.
template_id LLM classifier's pinned template match (match.template_id), stored on the draft row at insert. Kind decision: with a template → sandbox; infra without one → skip (can't boot).
task_type Set to ["BUILD"] by this pipeline. (PR_REVIEW comes only from the separate PR-review flow.) Kind decision: PR_REVIEW tasks are skipped for now — tour support deferred until the design is finalised.
expected_ports build_expected_ports(code_data) at draft-insert time — derived from docker-compose.yml + run.sh. Surfaces block: which sandbox.* links the model may use, with their real titles.
title, question Task-generation LLM output, already formatted in draft_payload["task_blob"]. Two-line task context in the prompt so the middle matches the scenario.

Where the tour value is passed

One direction, four hops: (1) generate_tour(...) returns the verified JSON dict right after the E2B gate passes → (2) creator.py holds it in memory through the solutions / draft-insert / GitHub stages (it needs nothing from them — its repo links are placeholders) → (3) creator passes it as the new optional tour= argument of mark_task_ready() in persistence.py, which adds it to the UPDATE dict → (4) Supabase stores it on the tasks.tour JSONB column in the same atomic UPDATE that flips status='ready'. Downstream, the candidate app reads tasks.tour, renders the sections as the walkthrough panel, and substitutes the {{variables}} at runtime (repo URL from the candidate's fork, sandbox URLs from the provisioned E2B sandbox). The pipeline never resolves variables — it only guarantees they're ones the runtime knows.

03

What a tour is — and what the LLM actually writes

A tour is a JSONB walkthrough stored on tasks.tour: an ordered list of sections, each holding steps of three types — markdown (a short instruction), link (a labelled URL, may contain a {{variable}}), and command (a shell command with an optional ≤3-line example output). Only the middle is generated per task.

Hard size cap: at most 7 sections total — fewer is fine, more is rejected. A tour is orientation, not documentation; a long tour overwhelms the candidate it's meant to help. The fixed head + tail already use 4 sections for sandbox tours (3 for local), so the LLM gets a budget of at most 3 middle sections (4 for local) and must pick only the highest-value ones. The cap is enforced in code at validation (§07) — an over-long tour fails and regenerates, it is never trimmed silently.

Head · fixed code

  • explore-code-base
  • access-code-editor
  • access-terminal

Injected verbatim per tour kind — never trusted to the model. (The local kind gets explore + clone-repo instead.)

Middle · generated LLM

  • build-and-run
  • run-tests
  • seed-data · inspect-database
  • open-redis · test-endpoints

Only the sections this task actually needs — grounded in its real files, ports, and service names. Selection rules in §06.

Tail · fixed code

  • submit

Kind-specific: push from /home/user/task (sandbox) or push from the cloned folder (local).

04

Where the new step lands in creator.py

The tour step sits directly after the E2B gate passes — the earliest moment the code files are final (the gate can regenerate the whole task on failure) and the latest moment the gate's sandbox is still alive to verify against. Each stage below tags the values the tour step consumes; all exist in memory by then. No GitHub round-trip needed.

  1. Generate task + code files LLM via Portkey

    Tech-specific prompt produces the scenario, README, and starter code.
    produces: code_files · title · question

  2. Eval gate evals.py · retry loop

    Task eval + code eval; failing tasks are regenerated.

  3. E2B build & test gate sandbox_eval · inside the retry loop

    The task must actually build and run in a sandbox. If it fails, the whole task is regenerated with different code — which is why the tour is not written before this point: it would go stale (or be wasted) on every failed attempt. Skipped for non-infra tasks.

  4. Generate + sandbox-verify the tour New step · generators/task/tour.py
    • Runs immediately after the gate passes, while the code files are final and — for infra tasks — the gate's sandbox is still alive.
    • Runs the core logic of §01: kind → file blob → prompt → validate → LLM eval judge.
    • Sandbox tours get a live check: the tour's command steps are executed in the same hot sandbox — build commands must succeed, service names must exist, the seed script must run, linked ports must be listening, run-tests must run (red is the expected start state). No extra sandbox boot.
    • Local tours get a deterministic manifest check: commands are cross-checked in code against package.json scripts / requirements.txt / pom.xml — no sandbox needed (§05 stack table).
    • A failing check → regenerate the tour with the failure as critique (bounded retries).

    Non-fatal by design: if every retry fails, tour stays NULL and the task still ships. A task that passed the eval gate and E2B gate must never die on a tour hiccup.

  5. Solutions + draft row insert_draft_task

    Docker detection and port derivation happen here (both pure functions of the code files — the tour step computes the same values a moment earlier).
    produces: is_shared_infra_required · template_id · expected_ports

  6. GitHub artifacts template repo · answer repo · gist

    Starter files pushed to the private template repo; solutions to the answer repo. The verified tour is simply carried in memory through this stage — it needs nothing from GitHub (its repo links are {{placeholders}}).

  7. Validate + flip to ready validate_task · mark_task_ready(…, tour=…)

    mark_task_ready gains an optional tour parameter — the tour lands in the same atomic UPDATE that flips status='ready'.

  8. Task is live — with its tour attached

    Candidates see the walkthrough from day one; no batch step, no follow-up script.

05

How the tour kind is decided

The kind determines the fixed head/tail, which middle sections are allowed, and which template variables the model may use. It is an ordered check — first match wins.

Important: infra vs non-infra is not re-guessed at tour time. The pipeline already decides a task's shape (task_shape: infra / non-infra) right when generation starts — it's what the E2B gate itself uses to decide whether to run. The tour step reuses that same determination, so the tour kind can never disagree with how the rest of the pipeline treats the task: an infra task always gets a correct sandbox tour, a non-infra task always gets a correct local tour — both first-class, from the same source of truth, with no drift between stages.

  1. 1 Does task_type contain PR_REVIEW? Deferred for now — how a PR-review tour should work isn't finalised yet, so no tour is written for these tasks. Support will be added once those decisions are made. skip — for now
  2. 2 Is is_shared_infra_required = true and a template_id set? The task boots an E2B sandbox from that template — the only case that gets editor / terminal / preview / DB-console steps. sandbox
  3. 3 Is is_shared_infra_required = true but no template_id? The task needs infra but cannot boot a sandbox — a tour would promise surfaces that don't exist. No tour is written. skip — no tour
  4. 4 Everything else (is_shared_infra_required = false) — this is where frontend tasks land. The candidate clones the repo to their own machine, works locally, and pushes to submit. No sandbox.* variables allowed. local

Frontend & non-infra tasks get tours too — the local kind

A React / Next.js / plain-frontend task generates no Docker files, so has_shared_infra_files() returns false → is_shared_infra_required = false → the decision above lands on local. The same applies to library-only backend tasks (LangChain, pure-Python). These tasks do get a full tour — just a different shape: no sandbox links, because there is no sandbox. The candidate accepts the GitHub collaborator invite, clones, runs locally, pushes to submit. The LLM's only job is the run section, with the real commands read from the repo's own files (package.json scripts, requirements.txt):

// Example LLM-generated middle for a React (Vite) frontend task — everything else is fixed boilerplate
[{"id": "run-project", "title": "Run the project", "steps": [
  {"type": "markdown", "body": "In the cloned folder, install dependencies and start the dev server."},
  {"type": "command", "label": "Install dependencies", "command": "npm install"},
  {"type": "command", "label": "Start the dev server", "command": "npm run dev",
   "output": {"type": "markdown", "body": "VITE v5.2.0  ready in 412 ms\n➜  Local:   http://localhost:5173/"}}]}]

Commands run locally in the cloned folder — never /home/user/task, never docker-compose. If the task is verified by a test suite, the section is run-tests (e.g. npm test, shown failing first) instead of, or after, run-project. Why sandbox.* is banned here: the candidate app's tour panel resolves those variables from a provisioned sandbox — with no sandbox, the panel would hang waiting for provisioning that never happens, so the assembler rejects such a tour outright.

Local commands are judged against the tech stack

The install / run / test commands are not generic — they must come from what the repo's own manifest files say, and the eval gate (§07) fails the tour if they don't match the stack:

Manifest in the repoStackExpected tour commands
package.json Node / React / Next.js / Vue npm install, then the real script names from its scripts block — npm run dev vs npm start vs npm run build, whichever this repo actually defines; npm test only if a test script exists.
requirements.txt / pyproject.toml Python / FastAPI / LangChain pip install -r requirements.txt, then the real entrypoint (uvicorn app.main:app, python main.py); pytest if a tests/ dir exists.
pom.xml / build.gradle Java / Spring mvn spring-boot:run / ./gradlew bootRun; mvn test / ./gradlew test.
go.mod Go go run . (or the real cmd/ path); go test ./....

The model reads these manifests in the file blob (config files are prioritised into it precisely for this), and the eval judge cross-checks: npm install in a Python repo, npm run dev when package.json has no dev script, or a pytest step with no tests in the repo — each is a failing verdict that triggers a regeneration with the critique attached.

06

How the middle sections are chosen (sandbox kind)

The model doesn't freestyle. The prompt gives it a fixed menu of section ids with a condition for each — it may only emit a section if the repo actually warrants it, in this order. Two conditions depend on the surfaces block: the prompt lists which of app_preview / db_console exist in this task's expected_ports, and forbids linking anything else.

And it has a budget: at most 3 middle sections (head + tail already take 4 of the 7-section cap). When more than 3 conditions match — say a repo with tests, a DB, Redis, and endpoints — the prompt tells the model to keep the ones the candidate can't succeed without, in priority order: build-and-run first, then run-tests (it defines success), then seed-data (no data = nothing works), and only then an inspection section (inspect-database / open-redis / test-endpoints). Fewer sections is always acceptable; a fourth middle section is a validation failure.

  • build-and-runeffectively always

    Setup only — bring the environment up, nothing else. Docker apps get the canonical trio: docker-compose up -d --build → docker-compose ps → docker-compose logs --tail=50 <service> with the real service name. If the app itself isn't a compose service (only the DB/Redis is), it's also started with its real command (uvicorn …, npm start). Never run.sh — that's the platform's internal boot script. No tests, no seeds, no verification here.

  • run-testsonly if a test suite verifies the task

    The real test command (pytest / jest / mvn test / go test…), shown failing first — the candidate sees the red state before starting — plus a one-line note to re-run after each change. Kept separate from build-and-run.

  • seed-dataonly if the repo has a seed script

    Runs the repo's real seed script (seed_data.sh, seed.py, prisma db seed…) after the services are up. Many stores start empty on a fresh docker-compose up (Firebase emulators, fresh DB volumes) — without this the candidate sees no data. Notes that re-running re-seeds.

  • inspect-databaseonly if real SQL/Mongo DB + db_console surface

    Link-only: the {{sandbox.db_console_url}} (Adminer) link plus one markdown line with the real login — System / Server / Username / Password / Database, read from the docker-compose env. No psql / mongosh / SELECT commands. If db_console isn't in expected_ports, the section is omitted entirely.

  • open-redisonly if the repo uses Redis

    docker-compose exec <service> redis-cli with the real compose service name, then a few orienting commands — DBSIZE, SCAN 0 MATCH <real key prefix>:*. Redis has no web console, so unlike SQL it keeps its shell commands.

  • test-endpointsonly if HTTP routes + app_preview surface

    Always leads with a docs link: Swagger/OpenAPI ({{sandbox.preview_url}}/docs) when the framework serves it (FastAPI, NestJS, springdoc…), otherwise a real route. May add one short curl health check after the link.

  • write-designonly if the deliverable is a design doc

    If the task asks for DESIGN.md rather than running code, a single write-design section replaces the menu above.

Tone rules baked into the prompt: one short sentence per markdown body, few steps per section, example outputs optional and ≤3 lines grounded in the repo's real values — never invented package counts, install warnings, or log dumps, and never a DB / endpoint / service the repo doesn't have.

07

Quality gates: validation + eval + live verification

Three layers stand between the model's output and the database. Layer 1 is deterministic code — schema and rule checks that cost nothing. Layer 2 is an LLM eval judge — the same gate pattern the pipeline already uses for tasks and code (evals.py). Layer 3 is empirical — the tour is checked against reality: executed in the gate's sandbox (sandbox tours) or cross-checked against the repo's manifests (local tours). A tour must pass all applicable layers; any failure means no tour is written (never a half-valid one).

Layer 1 — deterministic validation (code, runs first)

  • Shape: every section has id, title, and a non-empty steps list; every step is one of markdown / link / command.
  • Boilerplate ownership: if the model emits a head/tail section anyway (explore-code-base, submit, …) it is silently dropped — the code-owned version always wins.
  • No filler: sections like "understand-the-codebase" or "review-reference-material" are rejected — every section must be a concrete action.
  • Variable allowlist: every {{variable}} in the assembled tour must be one of the seven the runtime can substitute — repo.url, repo.clone_url, candidate.github_username, sandbox.editor_url / terminal_url / db_console_url / preview_url. Go-template dots in shell commands (e.g. docker ps --format '{{.Names}}') are excluded from the check.
  • Size cap: total sections ≤ 7 (sandbox: 4 fixed + ≤3 middle; local: 3 fixed + ≤4 middle, typically 1–2). Fewer is fine; more is a hard fail that triggers regeneration — never a silent trim.
  • Kind guard: a local tour must contain zero sandbox.* variables — with no sandbox to resolve them, they would hang the tour panel.
  • Final shape: the assembled tour is {enabled: true, version: 1, sections: [head + middle + tail], variables: […]} — the variables list holds only the placeholders actually used.

Layer 2 — the tour eval gate (LLM judge, runs on the assembled tour)

Layer 1 can only prove the tour is well-formed; it cannot prove the tour is true. The eval judge gets the assembled tour plus the same repo blob the generator saw, and returns a structured verdict (passed + per-check findings + a critique). It checks:

  • Groundedness: every command, service name, port, file path, DB name, and login in the tour actually exists in the repo — nothing invented. A docker-compose logs app when the compose service is called api is a fail.
  • Completeness: nothing the candidate needs is missing — a test suite in the repo but no run-tests section, a seed script but no seed-data, HTTP routes + preview surface but no test-endpoints.
  • No over-promising: no section for a capability the task lacks — no DB inspection for a repo without a DB, no endpoint testing for a worker with no HTTP surface.
  • Kind fit: a local tour tells the candidate to run things in the cloned folder (never /home/user/task or docker-compose the repo doesn't have); a sandbox tour never tells them to clone.
  • Stack fit (local tours especially): the install/run/test commands match the repo's manifest — npm commands only with a package.json and only its real script names, pip/pytest only for a Python repo, mvn/gradle only for Java. npm run dev when no dev script exists is a fail (§05 stack table).
  • Compactness: even under the 7-section cap, every section must earn its place — a padded tour with low-value steps fails. Fewer, sharper sections beat more, thinner ones.
  • Candidate-safety: the tour never leaks the solution — it orients (how to run, where to look), it does not solve (what to change).

Layer 3 — empirical verification (runs where the candidate will run)

Sandbox tours — executed live. The tour is generated right after the E2B gate passes, while the gate's sandbox is still running with this exact task loaded. Each command step is executed there, with per-section expectations:

  • build-and-run: every command exits 0; docker-compose ps shows the services the tour names; the logs command targets a service that exists.
  • seed-data: the seed script exists and exits 0.
  • run-tests: the test command runs (runner found, tests collected) — a red result is expected and correct; only "command not found" / "no tests collected" fails.
  • open-redis: redis-cli reaches the named service; the orienting commands return.
  • Linked surfaces: every port behind a {{sandbox.preview_url}} / {{sandbox.db_console_url}} link is actually listening.

Local tours — manifest cross-check in code (no sandbox exists for non-infra tasks; the gate is skipped for them). Deterministic, no LLM: each command is checked against the repo's own files — npm run <x> requires an <x> script in package.json; pip install -r requirements.txt requires that file; pytest requires tests; mvn/gradle/go require their manifests (§05 stack table).

On any failing verdict (judge or empirical): the failure is fed back into the generation prompt and the middle is regenerated — up to MAX_TOUR_EVAL_RETRIES attempts (mirroring MAX_EVAL_RETRIES in evals.py). If every attempt fails, no tour is written (tour = NULL) and the task still ships — the gates protect candidates from a wrong tour; they never block a good task. All LLM calls go through Portkey and verdicts are logged, so failing tours are auditable.

08

Design decisions

Self-contained module — no backfill dependency

All tour logic is written into generators/task/tour.py. The backfill script is reference only and will be deleted; nothing imports from it, so its removal breaks nothing.

Non-fatal, always

A task that passed the eval gate and the E2B gate must never die on a tour hiccup. Failure → warning log → tour stays NULL → the task still ships.

Ground in memory, not GitHub

upload_files_to_github pushes exactly code_data, so generating from memory is byte-identical to re-fetching from the repo — minus the API calls, rate limits, and latency.

Portkey, not raw Anthropic

The repo rule is all LLM traffic goes through the Portkey gateway. The tour step reuses openai_client from _clients.py — tracing and billing for free. The reference script's direct api.anthropic.com call is not carried over.

Boilerplate stays deterministic

Head and tail sections are assembled in code, never generated. Every candidate sees the same setup and submit steps; the model can't drift them.

All-or-nothing writes

Validation runs before assembly, assembly before the eval, the eval before persistence — a tour that fails any layer is discarded whole. tour is either NULL or fully valid, never partial.

Eval-gated, like tasks themselves

The pipeline already refuses to ship an unevaluated task; it now refuses to ship an unevaluated tour. LLM judge + retry-with-critique (like evals.py), plus an empirical layer: sandbox tours are executed in the gate's live sandbox, local tours are cross-checked against the repo's manifests (§07).

After the gate, not before it

The E2B gate sits inside the task-regeneration loop — a failing gate throws the code away and regenerates. Writing the tour before the gate would waste an LLM call per failed attempt and risk a stale tour. Right after the gate passes is the earliest safe moment — and the sandbox is still hot for verification.

Infra and non-infra are equal citizens

The step runs for every task the pipeline creates. Docker/shared-infra → sandbox tour; frontend and library-only tasks → local tour, with commands judged against the repo's tech stack. Skipped only for infra-without-template (sandbox can never boot) and PR_REVIEW (deferred until its tour design is finalised).
