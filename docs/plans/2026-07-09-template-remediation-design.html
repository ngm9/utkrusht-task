When a competency has no template

What the pipeline does today when it can't find infrastructure for a task (like S3), and what we're proposing to add so it can extend or build one as part of the pipeline run — not as a one-off manual fix.

exists today proposed addition needs a decision

What happens today

Every task needs a real sandbox to run in — a template. When the pipeline generates a task for a competency, it asks an LLM classifier: "does an existing template support this?" For S3, the answer was no, and the pipeline stopped cold.

1 · classifyPipeline asks: does any built template support this competency?
afterOne quick LLM call reads what every existing template already supports and answers yes/no. The answer gets saved against this exact competency + level, so the next time anyone asks for the same combo, the pipeline doesn't have to ask again — it just replays this same answer.
↓
2 · no matchClassifier replies: no template fits. Closest is utkrusht-infra, but it's missing s3 / aws-s3.
afterThat "closest template" name is only a guess in a sentence — nothing in the pipeline reads it or acts on it. It's there for a human to notice, not for the pipeline to use.
↓
3 · hard stopPipeline aborts. No GitHub repo, no task row, nothing created. Just a log line.
afterBecause the saved answer from step 1 says "no" for this combo now, every future attempt to generate an S3 task hits the exact same wall immediately — until a person manually fixes the template and clears that saved answer.
This is on purpose, not a bug. A past task (RabbitMQ) once got matched to a template that looked right but couldn't actually run it — candidates got a task with nothing working underneath. The hard stop exists specifically to prevent that from happening again. Any fix we add has to keep that promise: never claim a template supports something it doesn't actually run.

Why S3 specifically failed

utkrusht-infra already runs Postgres, MySQL, MongoDB, Redis, and Elasticsearch inside its sandbox. It does not run anything that can act like S3 — no MinIO, no LocalStack. So this isn't a missing checkbox somewhere; the actual capability doesn't exist inside the sandbox yet.

Does the pipeline already build templates in real time? Yes — for one narrow case

There already is a mechanism that builds a template mid-run, without any manual step. It just didn't apply here. The classifier's answer actually carries two different, separate pieces of information, and only one of them the pipeline acts on automatically:

confident matchClassifier is sure a specific template fits, and a human has already written that template's build instructions on disk — it just hasn't been built yet.
afterThe pipeline builds it right then, in the same run (~10 minutes), registers it, and continues — the task that triggered this still finishes in one go.
no match (S3's case)Classifier isn't sure anything fits, and only offers a guessed name for what might be closest.
afterNothing. The pipeline doesn't check whether that guessed name has build instructions written anywhere, because it never looks at the guess at all — that's the exact gap the proposal below closes.

What we're proposing to add

Instead of stopping at "no match," the pipeline gets one more step: a chance to fix the gap itself, before giving up — either by teaching an existing template a new trick, or by standing up a new one. Either way, nothing is trusted until it's actually tested.

1 · classifySame as today — ask if any built template supports this competency.
afterUnchanged from today: cheap, fast, and the result gets saved per combo.
↓
2 · no matchSame as today — classifier says no, but names the closest template and what's missing.
afterThe difference starts here: this time, the "closest template" guess is actually picked up and used, instead of sitting unread in a log line.
↓ instead of stopping here →
3 · new — decide how to fix itIs the missing piece a natural fit for the closest template (S3 → add it to the AWS/cloud template), or different enough that it needs its own new template?
afterProduces a concrete, written plan — which template to touch (or create) and what exactly needs to be added to it. Nothing has been built yet; this is still just a proposal on paper.
extend existing
Write the install steps for the missing service (e.g. add MinIO) into the existing template's build script.
build new
Write a whole new template from scratch, same pattern as existing ones.
↓
4 · build it for realActually provision the sandbox image (~10 minutes) — this machinery already exists (it's the same "confident match" builder from above), we're just triggering it from a new place.
afterA lock is held for the whole build so two pipeline runs can't try to build the same thing at once. If it crashes partway, it's cleaned up as a failure, not left in a stuck half-built state.
↓
5 · prove it worksDon't just check the install commands succeeded — actually start the service and confirm it responds (e.g. boot MinIO, then create + list a bucket for real).
afterThis is the step that decides everything below. Nothing is marked "supported" — and nothing gets to skip the hard stop next time — until this actually passes.
verified ✓
Template goes live. The original task (S3) now continues through the normal pipeline.
afterThe saved "no" answer from step 2 gets thrown out, so the very next competency of this kind — S3 again, or anything else that now fits — gets a fresh, correct "yes" instead of the old cached "no."
failed ✗
Falls back to today's behavior — hard stop, nothing created, logged for a human to look at.
afterSame safety net as today: no broken template gets registered, no task gets built on top of something that doesn't really work.

The one decision that matters

Steps 3–4 mean something is writing infrastructure install scripts and actually running them against a live environment, unattended, at real cost (~10 billed minutes per attempt). That's a bigger deal than everything else we've changed in this pipeline so far — those were all just wording in prompts. This is code that provisions real infrastructure.

Two ways to gate it

OptionHow it worksTrade-off
A · Autonomous Pipeline writes the install steps, builds, verifies, and activates the template in one run — no human involved. Fastest path to "S3 just works." Unreviewed provisioning code runs unattended.
B · Human-gated Pipeline writes the install steps and stops — a person reviews and approves. Only then does the real build run. One manual step per new capability (not per task — once S3 exists, every future S3 task just works). Safer.
Recommendation: Option B. The pipeline's own design already treats "no template found" as something meant for a human to act on, not something to route around automatically. Writing the fix automatically but requiring a human to press "build" keeps that safety net while still turning a dead-end into a queued, actionable fix instead of a silent log line.
