Proposed · under discussion

Open-Ended Task Flag

Problem, proposed solution, and the change in each pipeline stage. Companion diagram: docs/drawings/open-ended-task-flag.excalidraw.

The problem

Generated agent tasks are easy by construction, not by topic

The topics are genuinely intermediate (partial-failure reconciliation, fail-safe degradation, audit trails, taxonomy validation, bounded retries). The delivered difficulty is basic because the pipeline removes every decision a candidate would actually make — it hands over the answer at three points:

  1. Stub docstrings encode the exact contract — return shape, enum values, the file to edit, the rule to apply. e.g. build_diagnosis_context literally lists "overall_status": "complete"|"degraded"|"unknown" and says freshness is judged against config.READING_FRESHNESS_SECONDS.
  2. The grading tests ship inside the candidate repo — code_files contains invariants/·tests/, and the README says “make the invariant tests pass”. An open-book exam with the answer key attached — the candidate reads assert ctx["sensor"]["state"] == "ok" and copies the expected key/value.
  3. Objectives are an explicit checklist and policy constants are pre-set a policy constant is a hard-coded threshold/budget/taxonomy that encodes a decision the candidate should make: CONFIDENCE_FLOOR = 0.6 (config.py), PER_ATTEMPT_TIMEOUT_SECONDS = 2.0 / MAX_RETRIES = 2 (tools.py), READING_FRESHNESS_SECONDS = 300 (.env), and the state/status enums — all decided for them.
  4. The README and support fields walk them to the answer too — solution-shaped Helpful Tips, How to Verify steps that name the exact test cases, and definitions/hints that pre-name the solution's concepts. e.g. a tip: “…if the result shape made freshness explicit”, and “Explore the invariant tests to understand the behavior expected”; definitions defines “reconciliation”, “data freshness”, “overall health signal” — i.e. the building blocks of the fix.

The irony: the generator already tries to keep the README open-ended (HARD CONSTRAINT #2 forbids naming the API/library/pattern). But the stubs + shipped tests leak everything the README withholds — so the openness is cosmetic. Net: intermediate topic, basic difficulty — it measures transcription, not engineering judgment.

The proposed solution

A specification dial: the open_ended flag

Add one flag, decided once before generation (defaulted from proficiency, with an explicit override), that controls how much the task hands over. One flag → one task generated in that style — we do not build both variants.

  • open_ended = false — today’s behavior: explicit objectives, contract in stubs, grading tests shipped, policy constants given. Good for BASIC, and lets the gen-time gate verify solvability by running the shipped tests.
  • open_ended = true — symptom + repro README, bare stubs, no pre-set policy, and the grading tests are withheld from the candidate repo (only a thin readiness/RED smoke ships). Good for INTERMEDIATE+ and for differentiating engineers.

Why hiding the tests is safe: when a candidate finishes, we grade them by having an AI watch the recording of them working and read the code they wrote, then score it against a checklist — it never runs the test files (true for every task). So taking the tests out of the candidate's folder breaks nothing about grading; the only thing it changes is that the candidate can no longer open the tests and copy the answers. The one place we do run the tests is once, when we build the task, to confirm it can actually be solved — and for a hidden-tests task we just use our own private copy (kept in the separate answer repo the candidate never gets, see Stage 5). We also add a safety check while building: if the tests accidentally end up in the candidate's folder, the task is rejected and rebuilt.

Two layers — and don’t underspecify the problem: open-endedness is (1) hide the solution (the levers below) and (2) shape the task so it genuinely has design space — a scenario with more than one defensible architecture, with no single “expected shape” baked into the scaffold/fixtures. Stripping the spec off a one-true-answer task just makes it ambiguous, not open. And underspecify the solution, never the problem: the Task Overview / symptom stays crisp and fair — only the “how” (objectives-as-steps, tips, verify-cases, return shapes, thresholds) is withheld.

Subtlety for open tasks: because the candidate designs their own data shape, the held-back grader can’t assert internal keys like ctx["sensor"]["state"]. It’s behavioral / black-box instead — e.g. “feed the offline-gateway case and assert the final diagnosis does not claim healthy.” (And remember: prod grading never runs it anyway — only the gen-time solvability gate does.)

“No schemas.py” does NOT mean the candidate is blind to the data. Two different things get called “schema”. The database schema — init_database.sql (tables + seed rows), the complete read-only agent/db.py lookup tool, and run.sh (brings Postgres/Redis up with the seed data) — ships in both forms, so the candidate can always query the DB, run the agent, and reproduce the bug. What the OPEN form withholds is only the application contract (schemas.py): the shape of the agent’s own normalized record, report payload, and status vocabulary. So: OPEN = “here’s the raw data + a tool to read it — you design the output shapes”; CLOSED = “here’s the raw data and the exact output shapes to fill in.” The design decision is the engineering being tested — never the ability to see the data.
