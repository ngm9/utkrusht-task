How to read this page

Each competency has two live tasks on dev generated back-to-back: an Open one and a Closed one. The candidate clones the same kind of bug to fix in each — only the amount of the solution they're handed differs.

For each pair you'll see:

  • The bug in plain words — what the agent is failing to do.
  • The repo table with clickable GitHub links + answer repos.
  • The candidate's edit surface — the file they're meant to change, exact lines.
  • The ground-truth solution from the answer repo — so you can see what a complete solve looks like.
  • The leak table — what gets handed over in each form (incl. Phase 2's planned change).
Key idea (the "two schemas" clarification). "schemas.py" in code below always means the agent's application-level output contract (the typed report payload, the status enum). It does not mean the database schema — that ships in both forms (via init_database.sql, docker-compose.yml, and the read-only tool layer). So an open task never blinds the candidate to the data; it just stops handing them the answer of how the agent should structure its own output.

1 · Tool Use for Agents · INTERMEDIATE · Claude

What the bug actually is (same in both forms)

An AI agent that pulls a buyer's record from PostgreSQL and writes a one-paragraph briefing. It has two related defects:

  1. No cache reuse. Every request for the same buyer re-hits Postgres and re-runs every tool — the Redis layer is dead code.
  2. No grounding. When the lookup misses or returns an error, the agent emits a confident-looking report instead of a clear, honest status.

Same fix work either way; the question is whether the candidate is told the data shapes, the cache-version rule, and the status vocabulary in advance.

2 · Production Agent Engineering · INTERMEDIATE · Claude

What the bug is

An LLM "playback support agent" runs a plan-execute loop driven by a real LLM over Redis Streams. Three production problems are bundled in one task:

  1. No bound. The run loop can iterate forever — if the LLM plans badly, it burns Redis CPU unbounded.
  2. No observability. Nothing in Redis-Streams records what the run is doing at each step; support has no way to look.
  3. No clean stop. There's no surface for a stop request, so a runaway run can only be killed by killing the process.

3 · Context Engineering · INTERMEDIATE · Claude

What the bug is

A "dispatch copilot" answers carrier questions by combining a user question, the asking carrier's identity, and evidence retrieved from a local store (a single JSONL of operator notes + policies). It assembles the chat messages that go to the model. Three context-engineering problems are bundled in one task:

  1. Cross-carrier leakage. Evidence about other carriers' policies can end up in the prompt sent to the asking carrier.
  2. Prompt-injection obedience. Untrusted notes inside the evidence can contain "instructions" that the model follows.
  3. Token-budget overflow. Without a budget, large evidence blocks blow past the model's context window.

5 · What Phase 1 left open — and what Phase 2 / Phase 3 actually do

The dial works. All 7 candidate repos we generated flip exactly as designed. Three real leaks remain — visible in every pair's repo.

Leak 1 · The grading tests ship in the candidate repo. Both forms include them today (e.g. tests/test_tool_flow.py · 156 LOC of test code that asserts on shape; invariants/test_agent.py · 110 LOC that names buyer_id/"ok"/served_from_cache; tests/test_context_assembly.py · reveals the multi-concern shape). A candidate can read these tests to learn part of the answer.

Phase 2 fix. _split_grader_tests in generators/task/creator.py deterministically pops tests/·invariants/ out of the candidate code_files into a private grader_files bundle when open_ended=true. That bundle rides to the existing -answers repo (no new infra). The candidate repo ships only a thin readiness/RED smoke.

Why this is the tricky half. Once the tests are gone, the existing E2B build/test gate can't prove a task is solvable by "run the shipped tests to GREEN" — that signal disappeared. The gen-time gate must instead clone the answer repo, overlay the withheld graders onto a reference solution, and prove GREEN behind the scenes (the new "oracle gate"). This is the brand-new orchestration Phase 2 builds.
Leak 2 · Even open CLOSED forms technically leak via the tests. In the closed form the docstring enumerates the algorithm and the test asserts the spec was followed exactly. So the spec is handed over twice (once in the stub, once in the test). That's intentional for closed — but when withheld tests ship in the open form, the test still exposes the shape even though the stub doesn't. Phase 2's withhold removes that leak entirely.
Leak 3 · "'open' vs 'unfair/ambiguous' isn't gated. The doc's own warning: "stripping the spec off a one-true-answer task makes it ambiguous, not open." Phase 1's critic only checks for solution leakage; it doesn't check the inverse — that the task has genuine design space and a crisp, fair problem. Phase 3 fix: a new "open vs ambiguous" eval critic that scores whether the task admits several defensible architectures and the problem statement is unambiguous. Tighter than the leak critic; central to trusting open tasks at scale.
